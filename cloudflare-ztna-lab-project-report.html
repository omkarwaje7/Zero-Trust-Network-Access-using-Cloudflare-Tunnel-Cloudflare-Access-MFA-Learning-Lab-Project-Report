Cloudflare ZTNA Lab

Project Report  |  Zero-Trust Network Access using Cloudflare Tunnel, Cloudflare Access & MFA  |  Learning Lab

1. Project Overview

This project implements a hands-on learning lab that demonstrates Zero-Trust Network Access (ZTNA) using Cloudflare's commercial edge services. The core principle of ZTNA is that no user or device is implicitly trusted based on network location — every access request must be explicitly authenticated, authorised, and (where required) verified with a second factor before reaching the protected resource.

The lab uses a deliberately harmless Python Flask web application as the "protected resource." The application contains no real data, no real credentials, and no destructive operations. Its sole purpose is to act as a concrete target that can be secured, probed, and tested.

Objectives

  • Demonstrate how Cloudflare Tunnel creates an outbound-only encrypted channel — removing the need to open inbound firewall ports.
  • Show how Cloudflare Access enforces identity-based access policies at the network edge, before traffic reaches the origin.
  • Enforce multi-factor authentication (MFA) as a policy condition independent of the application.
  • Prove that binding the origin server to 127.0.0.1 prevents direct LAN access even when Cloudflare is bypassed.
  • Validate the full ZTNA control chain through nine explicit pass/fail acceptance criteria.

2. Architecture

Internet User │ ▼ Cloudflare Edge (Cloudflare Access) • Identity check via IdP (Google / GitHub / One-Time PIN) • MFA enforcement — requires mfaVerified: true • Allow/deny policy scoped to authorised email address │ (request proceeds only after policy passes) ▼ Cloudflare Tunnel (cloudflared — outbound only) • Encrypted outbound connection from local machine to Cloudflare • No inbound firewall rules needed • Terminates locally at http://127.0.0.1:8080 │ ▼ Waitress (WSGI server, bound to 127.0.0.1:8080 only) • Not reachable from LAN or public internet directly │ ▼ Flask Application GET /admin — read-only demo admin console (fake data + disclaimer) GET /healthz — returns {"status": "ok"} JSON

Trust boundary: The only network path from the internet to the Flask application passes through Cloudflare Access and the tunnel. Direct access to port 8080 from a LAN machine is prevented at the OS level by the loopback binding — no firewall rule is required.

Two read-only routes are defined using Flask 3.1.1. No app.run() call exists anywhere in the codebase — Flask's development server is structurally absent.

All user records use addresses in the @example.invalid domain, which is permanently reserved by RFC 2606 and can never resolve to a real mailbox. The page renders a visible warning banner: "THIS IS A DEMONSTRATION ONLY."

Waitress entry point — server.py

Waitress 3.0.1 is used in place of Flask's development server. The binding address is a hardcoded string literal: 

_HOST = "127.0.0.1"
_PORT = 8080
serve(app, host=_HOST, port=_PORT)

There is no environment variable, command-line argument, or configuration file that can change _HOST. Using waitress-serve app:app directly is explicitly warned against in the README because it bypasses this file and Waitress defaults to 0.0.0.0.

6. Key Design Decisions

MFA is not implemented in the application

This is intentional. MFA is enforced by the Cloudflare Access policy using the mfaVerified: true Require rule. Implementing MFA in the Flask app would be misleading: it would apply only to the loopback path (where Cloudflare is bypassed) and would be redundant on the public path (where Cloudflare already enforces it). The application is deliberately authentication-agnostic.

Loopback binding is a hardcoded literal

_HOST = "127.0.0.1" in server.py is a string constant, not an environment variable. This means changing the binding address requires a deliberate code edit — it cannot happen by accident through misconfiguration or a missing environment variable.

Cloudflare Tunnel requires no inbound firewall rules

cloudflared establishes an outbound-only persistent connection to Cloudflare's edge. The origin machine never listens for inbound connections from Cloudflare — traffic flows from the edge into the tunnel, not the reverse. This eliminates an entire class of exposure that traditional reverse proxies introduce.

RFC 2606 reserved domain for fake data

All demo user records use @example.invalid. The .invalid TLD is permanently reserved by RFC 2606 and will never resolve in DNS. It is impossible for these addresses to correspond to real accounts.

7. Cloudflare Account Steps Performed

The following steps were carried out in the learner's Cloudflare Zero Trust dashboard and are not automated by the repository. Each is marked CLOUDFLARE ACCOUNT REQUIRED in the README.

  1. Installed cloudflared on the lab machine.
  2. Created a tunnel named ztna-lab-tunnel in the Zero Trust dashboard.
  3. Configured a public hostname routing yourdomain.example/ to http://127.0.0.1:8080.
  4. Ran cloudflared tunnel run --token <TOKEN> — token stored in memory only, never committed.
  5. Created a Cloudflare Access self-hosted application scoped to yourdomain.example/admin.
  6. Configured an Identity Provider (One-Time PIN or equivalent).
  7. Created an Access policy: Include rule = authorised email; Require rule = mfaVerified: true.
  8. Verified the Access application showed Active status in the dashboard.

9. Conclusions

The lab successfully demonstrates a complete Zero-Trust Network Access architecture using Cloudflare's edge services. Several properties that are difficult to achieve with traditional VPN or reverse-proxy approaches are confirmed:

  • No inbound firewall rules required. The tunnel is entirely outbound.
  • Authentication enforced at the edge, not the application. The Flask app performs zero identity checks and remains completely stateless.
  • MFA is a policy condition, not an application feature. It cannot be bypassed by manipulating the application.
  • LAN isolation is structural. Binding to 127.0.0.1 provides a guarantee that no firewall rule can accidentally override.
  • Resilience is testable. The tunnel can be stopped and restarted with predictable, observable results.

The codebase contains no real credentials, no real user data, no destructive operations, and no deployment automation. It is suitable for sharing as a learning resource.
